# Release signing and distribution

## Proposed private publishing runbook

**Documentation only; not configured.** No signing/publishing workflow is present in this checkout. The following is the proposed GitHub Free/private-repository setup, not an instruction to create credentials or enable automation without separate authorization.

1. **Establish the trust and cost boundary.** Keep the repository private and verify its live visibility before every release upload; release assets require authenticated repository access, not an anonymous download link. Under the assumed GitHub Free/private plan, this design has no enforced environment required-reviewer gates: a manual trigger is **not** a reviewer approval gate. Anyone authorized to edit the workflow can change it to exfiltrate repository secrets; owner/account compromise remains a trust boundary. Restrict workflow/contributor access and protect `main`. Check current included Actions-minute and artifact-storage quotas, use short artifact retention and concurrency limits, and disable paid usage or set appropriate hard controls so overages cannot incur unapproved charges. Free does not mean unlimited.
2. **Prepare a stable release identity outside GitHub.** With separate authorization, create a dedicated Auto ExecSec keystore using standard Android/Java tooling, outside source/build/toolchain folders, with restrictive local access. Keep independent encrypted, recoverable backups of the key and its passwords outside GitHub; verify recovery before relying on it. Record the expected certificate fingerprint. Retain the same dedicated key for future updates. The current debug-signed installations cannot update in place to this different release signature; installation/data-transition decisions require separate authorization, not an automatic uninstall.
3. **Configure narrowly scoped credentials.** Use an approved local credential process and GitHub's secret-input UI, never chat, source files or command-line secret arguments. Proposed repository Actions secrets contain only the dedicated keystore encoded as base64, its store/key passwords and alias. Base64 is transport encoding, not encryption. Keep the expected public certificate SHA-256 and reviewed package/permission metadata separately from secret values. Never upload the debug keystore. This proposed cloud-key design would change the earlier keep-key-outside-GitHub choice and therefore requires explicit authorization before implementation; this runbook alone does not grant it.
4. **Build without secrets.** A future workflow must accept `workflow_dispatch` only, with explicit `verify` or `release` mode, expected full source commit and version inputs. Reject any ref other than current protected `main`; no automatic push, PR or tag publishing. Pin third-party actions to reviewed full commit SHAs and checksum-verify downloaded signing tools against reviewed expected checksums. Default job tokens to read-only (`contents: read`) or no permissions where possible. A secret-free job checks out the exact commit, runs tests/lint and builds an **unsigned, non-debuggable release APK**, not the debug APK. Record source commit, run ID, immutable artifact ID and SHA-256 plus extracted version/package/permission metadata; do not identify inputs solely by an artifact name or "latest".
5. **Isolate signing and verify the result.** A separate clean, ephemeral job downloads only that run's exact unsigned artifact ID and verifies its hash/provenance before signing. It receives signing secrets only in the signing step: no project checkout, Gradle/project-source execution, restored caches or untrusted scripts while secrets are available. Decode credentials to restricted temporary files, avoid shell tracing/secret output, use supported secret injection rather than passwords in process arguments, and clean up afterward. Align before signing; verify final alignment, APK signature and expected certificate fingerprint, `local.reminders`, expected versionName/versionCode, non-debuggable status and the reviewed permission allowlist. That allowlist includes the app's legitimate SMS-send, phone-state, notification, exact-alarm and boot permissions plus its signature-protected receiver permission; it is **not** a no-permission APK. Reject unexpected permissions. Produce the signed APK and `SHA256SUMS`, with their exact hashes and provenance. A valid signature identifies a signing key and protects integrity; it does not attest that code is benign or guarantee SMS permission/delivery.
6. **Run verification first, then deliberately release.** After reviewing the workflow and exact `main` commit, the owner manually dispatches `verify` mode, which performs build/sign/verification but creates no tag/release. Inspect test/lint results, artifact IDs/hashes, package/version, permission diff and certificate fingerprint using authenticated Actions access. For publication, manually dispatch `release` mode with the reviewed exact commit/version and expected signed-APK hash; verify again and refuse publication if outputs differ. Enforce a strictly increasing versionCode against prior published metadata, a coherent unique versionName/tag, and no existing tag or release for that version. Serialize release runs and recheck that `main` still points to the reviewed commit immediately before tagging/upload; refuse changed `main`, never silently select a newer commit or overwrite a tag/release.
7. **Publish only the verified deliverables.** Only the separate publishing job receives `contents: write` through the ephemeral `GITHUB_TOKEN`; it receives no signing secrets and executes no project code. Verify live private visibility, exact source commit/tag, immutable signed artifact ID and hashes again. Create the tag at that exact commit and a private-repository GitHub Release containing **only the verified APK and `SHA256SUMS`**. Release notes identify source commit, workflow run, version and public certificate fingerprint. Never attach keystores, passwords, raw build logs, test tools, import data or whole build folders. Verify the resulting release/tag and authenticated asset downloads against their hashes; on partial failure, report it and require review rather than silently overwriting assets or retrying publication.

## Future public publishing approval requirement

**If the repository becomes public, add enforced owner approval gates to BOTH signing and publishing jobs before enabling public release automation.** Reassess signing/repository secrets, workflow permissions and contributor access first. Configure required-reviewer environments for both jobs, restrict deployments to protected `main`, and require the owner to review the exact source commit and artifact hashes/provenance before approval. Signing approval must cover the exact unsigned artifact; publishing approval must cover the resulting verified signed APK and checksum. Do not allow automatic agent approval or approval bypass; if the available plan/settings cannot enforce these controls, leave public release automation disabled. Changing visibility does not enable these gates automatically.
